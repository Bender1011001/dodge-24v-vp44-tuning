## The two modules

Both controllers are Cummins **CM551**, Chrysler/Dodge ISB VP44 application, same ECM P/N and same ROM date. The silk-screened ECM **code** and the calibration date differ. That is why they were dumped side by side.

| Field | A | B |
|---|---|---|
| ECM | CM551 | CM551 |
| ECM code | J90269.06 | J90268.04 |
| Dataplate engine | Cummins 6BTA 5.9 (`JCMMNS6BTA5.9 Li`) | ISB 235 (`JCMMNSISB 235`) |
| Fuel pump / plate code | FP98455 | 98453 |
| Application | Chrysler T-300 | Chrysler automotive |
| ECM P/N (ITN `0001`) | 03942336 | 03942336 |
| ROM date (ITN `0002`) | 091197 | 091197 |
| Cal date / DATADATE | 062800 | 102198 |
| Hardware id (ITN `0000`) | `45 31` | `45 31` |
| SSPH (ITN `107E`) | `05 07 10 11 05 00 02 00` | `05 07 10 08 05 00 02 00` |
| SSBLPH (ITN `11B2`) | `02 01 02 08` | `02 01 02 08` |
| FLCRC (ITN `1043`) | `00 00` | `00 00` |
| Engine hours | 13130:48:02 | 10196:32:59 |
| Key-on | ~13724 | ~10240 |
| ECM VSS miles | ~81 | ~287919 |
| Catalog used | Chr0000 KennPar (ReadByNTN) | same |
| ITNs ok / miss | 667 / 0 | 667 / 0 |

VIN and engine serial are **not** published. Packed dumps redact ITN `81AC` (vehicle id / related counters). Password and boot-copy ITNs were never requested.

JSON copies: [maps/A_identity.json](../maps/A_identity.json), [maps/B_identity.json](../maps/B_identity.json).

## Identity ITNs that are safe to talk about

These are the fields used to name a box without publishing VIN/ESN.

| ITN | Name | Role |
|---|---|---|
| `0000` | hardware / cal-page id | Two bytes `45 31` on both |
| `0001` | ECM_PN | ASCII `03942336` |
| `0002` | ROM_DATE | ASCII `091197` |
| `0003` | CAL_DATE | ASCII `062800` vs `102198` |
| `0006` | DAT_PLAT | 818-byte dataplate (engine string, pump, ECM code, Chrysler application, Cummins PNs) |
| `001D` | DATADATE | Same six-byte ASCII date as CAL_DATE on these boxes |
| `001C` | HOUR_MTR | Engine hours (runtime; differs) |
| `1043` | FLCRC | Flash checksum field; both dumps returned `00 00` on this read |
| `107E` | SSPH | Software version blob; A and B differ at byte 3 (`11` vs `08`) |
| `11B2` | SSBLPH | Bootloader version blob; matches |

Early lab notes mis-labeled ITN `0022` as ECM_ID. On this Chr0000 map `0022` is **ADJPSWD6**. It was skipped. Hardware identity for these pulls is ITN `0000`.

DAT_PLAT is a blob (`0x332` / 818 bytes in the packed dump), not a single ASCII line. The engine, pump, ECM code, and Chrysler application strings above were parsed from that blob. Cummins internal part-number runs also appear in the plate (for example `39494491` and neighbors on A). Those are dataplate contents, not a second ECM P/N.

## Hours versus miles

ECM A reports on the order of **13,130 engine hours** and only **~81** ECM VSS miles. ECM B reports **~10,197 hours** and **~287,919** ECM VSS miles. Those are values stored in the controller, not odometer photographs. A low VSS mile count with high hours is consistent with a box that spent a long time running without a vehicle-speed input the ECM trusted, or with a module that did not live its whole life in the truck that currently holds it. This writeup does not claim a vehicle history from those two numbers.

Hours, key-on, and VSS are **runtime counters**. They differ because the boxes lived different lives. They are not calibration maps.

## What a KennPar dump is

A **KennPar / ReadByNTN dump** is a dictionary of parameter IDs (ITNs / NTNs) to the bytes the ECM returned. Each record in `maps/A_dump.json` / `maps/B_dump.json` is:

- hex ITN key (for example `"1041"`)
- catalog name(s)
- byte length
- hex payload (omitted when redacted)

That is **not**:

- a flash / ROM image
- an INSITE “ECM Image” (`.eif`)
- an INCAL package
- a Calterm `.xcal` / download file
- something you can program onto another ECM from this repository

INSITE Features/Parameters and ECM Image Analyzer are the **service** view: identity, monitors, a handful of adjustable items. An INSITE `.eif` captured on this bench was a **4 KB encrypted ZIP work-order snapshot**. It is not flash and not the KennPar set.

Calterm **Upload**, with a current license and the Dodge E2M maps, is the **engineering** view: thousands of scalars, axes, and tables. There is no working Calterm license in this project, and the copyrighted E2M metafiles (`Chr0000.e2m` / `Chr9900.e2m`) are **not** in this repo.

What was done instead: a read-only INLINE 6 client requested a **subset** of Chr0000 KennPars that the ECM would answer — **667 ITNs, 0 misses** on each box, about 28.5 seconds. Password ITNs and the boot-copy destination ITN were omitted from the request list. The packed JSON is that answer set.

Raw payload comparison after VIN redaction: **536 identical**, **130 different**. A different ITN blob is not automatically a different decoded map. Trailing bytes past a table, runtime counters, and dataplate strings account for many of the 130. The decoded fuel/timing story is in [factory-fuel.md](factory-fuel.md) and [factory-timing.md](factory-timing.md). Storage rules: [maps.md](maps.md).

## Catalog era

Two Dodge E2M product lines exist in the Calterm 4.7 metafile tree (not redistributed here):

| File | Product | Era (as labeled in the lab) |
|---|---|---|
| `Chr0000.e2m` | A3A4 | ~2000–2002 |
| `Chr9900.e2m` | F380 | ~1998.5–1999 |

Chr0000 was used first for J90269.06. It answered 667/667. The same list was used for J90268.04. That does **not** prove the silk-screen codes are “2000 vs 1998” in a marketing sense; it proves this readable subset is valid on both boxes.

NTN on the wire is the E2M third CSV field, **hex**. `DATADATE = 1D` is the sanity check that these are not decimal Calterm ITNs with a different numbering.

## What this dump cannot do

- It cannot recover erased flash, bootloader contents, or a programming password.
- `FLCRC` coming back as zeros does not mean the cal is blank; it means this ITN read is not a useful checksum for these boxes.
- It cannot tell you how to write a table. Writing is out of scope on purpose.
- Hybrid-governor and several other Z-maps **NAK** on this Dodge calibration. Absence of a table in the decode is often “not implemented on this cal,” not “read failed randomly.” See [maps.md](maps.md).
